## 标准尺寸 hw_emu 性能

完整随机权重 decoder layer 的 `.cw1` 活跃区间为 2,278.671 µs。以 hw_emu 的 300 MHz 时钟模型换算：

| 指标 | `.cw1` | 未重叠基线 | 变化 |
| --- | ---: | ---: | ---: |
| 周期/layer | 683,601 | 714,495 | -30,894（-4.32%） |
| 200 MHz 等效延迟 | 3.418 ms | 3.572 ms | -4.32% |
| 200 MHz 等效吞吐 | 22.55 GMAC/s | 21.57 GMAC/s | +4.54% |

“等效”表示用仿真周期除以目标频率，并非真实板卡实测。

## 标准尺寸 8-token prefill

2026-07-23 使用随机 Fix16 权重完成了一个标准 Qwen decoder layer 的
8-token prefill hw_emu。测试覆盖：

- attention/FFN RMSNorm；
- Q/K/V projection 和 RoPE；
- position 0..7 的 causal online FlashAttention、KV cache、QK/PV；
- O projection、attention residual；
- Gate、Up、SiLU-mul、Down 和最终 residual。

所有张量比较通过。Q/K/V/O/Gate/Up 的最大 raw error 为 0 或不超过 1，
Down/FlashAttention 不超过 4；48 个 attention MM task 和 1536 个结果 packet
全部完成。最终 hidden checksum 为 `0xb72a92cb5224f0c7`。

hw_emu profile 给出的四个 kernel 总活跃区间为 3176.997 us。该 xclbin 的
kernel clock 为 200 MHz，对应约 635,399 cycles：

| 指标 | 2-token | 8-token |
| --- | ---: | ---: |
| active interval | 2806.029 us | 3176.997 us |
| cycles @ 200 MHz | 561,206 | 635,399 |
| useful MAC | 154.15M | 616.71M |
| effective throughput | 54.94 GMAC/s | 194.12 GMAC/s |
| 双 CU 物理峰值利用率 | 26.82% | 94.78% |
| 摊销时间/token | 1403.0 us | 397.1 us |

从 2 token 增至 8 token，工作量约增加 4 倍，而 kernel active interval 只增加
13.2%；吞吐和每 token 摊销性能提高约 3.53 倍。这表明 M=8 能填满阵列的
8 行，weight load、stream drive、compute 和跨 wave collect 已形成有效重叠。

此前 6,379,917-cycle、9.44% 利用率的数据是旧版本的分阶段外推，现已由本次
实测替代。详细口径见 `docs/8-token_Prefill_hw_emu性能_20260723.md`。

### 多 token RTL 修复

首次正常尺寸运行暴露出一个 HLS 综合语义问题：将完全分区的
`[token][block]` GBUF 扁平为裸指针后，CSim 正确，但 RTL projection 只可靠
保留 token row 0。当前实现通过模板化 buffer 类型并使用显式
`source.block[token][block]` / `destination.block[token][block]` 访问修复。

修复后已通过 15-case CSim、开启 deadlock detection 的 13/13 C/RTL CoSim、
controller NK CSynth/XO export、2-token hw_emu 和上述 8-token hw_emu。

本次 prefill 使用的是保留全部分算子 profile 路径的诊断 controller，而不是
资源精简的 `CC8_RESIDENT_LAYER_ONLY=1` 镜像。诊断版本顶层 HLS 估计为
3.839 ns（260.48 MHz）、1586 BRAM18、248 DSP、2,405,836 FF、1,021,326 LUT；
FF/LUT 已分别达到 U50 全器件的约 137%/117%，因此它证明了功能和流水效率，
但不能直接作为当前可部署实现。下一步必须把同一 prefill 流程固化到 resident
静态调度，并删除互斥的 profile 控制/缓存副本。

## HLS 结果

当前资源精简的 resident `.cw1` controller HLS 估计：

| 项目 | 结果 |
| --- | ---: |
| estimated clock | 3.746 ns（266.93 MHz） |
| BRAM_18K | 488 |
| DSP | 90 |
| FF | 421,880 |
| LUT | 390,283 |

投影数据流局部估计约 3.182 ns。当前主要时序/II 风险不在块级 kernel 接口，而在 `accumulate_cc8_flash_pv_one_core`，其 II 为 4；该路径包含在线 Softmax 后的 PV 累加、归约和状态更新。

8-token prefill 诊断 controller 的资源不能与上表混用：它为保留逐算子测试入口
编译了额外通路和多 token GBUF，HLS 估计为 1586 BRAM18、2.41M FF 和
1.02M LUT，当前不可部署。94.78% 是其 hw_emu 数据通路效率，不代表已经完成
U50 place-and-route。

## 下一步

1. 将当前分算子 prefill profile 固化为资源精简的 controller 单次整层静态调度，删除互斥 profile 通路和重复 GBUF，并重新综合确认资源可部署。
2. 扩展到多 block 和长 context，量化 attention tile 数量增长后的周期变化。
3. 优化 FlashAttention PV 累加的依赖链和 bank/归约结构，保持数值误差约束。
4. 实现 Split-M 或多请求并行，提高单 token decode 的物理 lane 利用率。
5. 在 SC 正常的 U50 上重新验证 200 MHz 镜像，再逐步提高频率。
6. 用真实 3B 权重验证跨 HBM bank 的完整容量映射和多 layer 稳定性。
